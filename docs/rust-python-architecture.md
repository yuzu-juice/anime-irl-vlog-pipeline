# Rust / Python Architecture

`irl` separates the application layer from the AI inference layer.

## Rust

Rust owns the product shell:

- project files
- cache
- timeline state
- job orchestration
- ffmpeg control
- worker lifecycle
- desktop packaging

Rust should make the app stable, portable, and easy to distribute.

## Python

Python owns AI inference:

- pose extraction
- character frame generation
- segmentation
- depth estimation
- ComfyUI integration
- CUDA / torch workloads

Python is treated as an internal worker runtime, not the main application.

## Bridge

Start with a simple subprocess bridge:

    Rust -> Python worker -> output files / JSON

Later, upgrade to a persistent worker:

    Rust -> local Python service -> JSON-RPC or HTTP

## Principle

Rust is the app.
Python is the AI engine.

## Worker Lifecycle

Rust manages Python workers as child processes:

    Rust spawns -> Python process -> Rust waits / kills on timeout

Each worker is stateless. State lives in files on disk.
Rust never keeps a Python process alive across shots unless it is a
persistent service.

## Communication Protocol

Subprocess phase:

    stdin:   newline-delimited JSON job descriptors
    stdout:  newline-delimited JSON progress / result lines
    stderr:  captured and logged by Rust
    exit 0:  success, outputs written to agreed paths
    exit !0: failure, Rust reads stderr for diagnostics

Persistent phase (upgrade):

    HTTP POST /job        submit a job descriptor, get job_id
    GET  /job/:id/status  poll progress
    GET  /job/:id/result  fetch result metadata

The JSON schema is shared between Rust and Python via a single
source of truth (JSON Schema file or Rust struct -> Python pydantic).

## Error Boundary

Python failures must not crash the Rust shell.

Rust treats every Python invocation as fallible:
- non-zero exit -> retry up to N times, then surface to user
- timeout -> kill process, retry, then surface
- malformed output -> log, mark job failed, do not retry

User-visible errors are always generated by Rust.
Python errors are translated into user-facing messages by Rust.

## GPU and Device Management

Rust does not touch CUDA, Vulkan, or Metal.

Python workers own device selection:
- CUDA_VISIBLE_DEVICES
- VRAM budgeting
- mixed precision
- batch size tuning

Rust only controls how many workers run concurrently
(based on available VRAM, configured by the user).

## Development Workflow

During development, both sides are iterated independently:

    # Rust
    cargo run -- --project /path/to/project

    # Python worker (standalone, for testing)
    python -m irl_worker --job job.json --output /tmp/out

Integration tests run both sides together:

    cargo test --test integration  # spawns Python workers

Rust tests that do not need Python can use mock workers
that write pre-baked output files.

## Why Split

- Rust binaries ship without a Python runtime. Users install Python
  separately or use an embedded Python (future).
- Python dependencies (torch, CUDA, ComfyUI) are heavy, fragile, and
  platform-specific. Keeping them out of the Rust build avoids
  coupling the app shell to the ML stack.
- Workers can be swapped without recompiling the app.
- The split forces a clean API boundary, which makes the pipeline
  inspectable and cacheable at every stage.
